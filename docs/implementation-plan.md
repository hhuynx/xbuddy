# XBuddy 实现方案

版本：v0.7 Python 方案；日期：2026-10-11。

本文件依据《13_投资XBuddy.md》制定。文档中的功能与交付要求作为验收依据；技术栈、界面布局、场景和阈值为本方案的实现选择。采用用户要求的 Python 技术栈，不设题目中的时间限制。第一至第六批建立运行底座；用户试用指出的基础问答、澄清、目标检查及综合回答现已补齐，最新实际范围见 [核心修复记录](agent-core-readiness.md)，原诊断保留在 [基础能力复核](agent-capability-review.md)。第七批公开交付、部署条件与 iFinD 待验证。

## 1. 产品定位与首版范围

XBuddy 是面向个人投资研究者的 Agent 工作台。用户提出研究目标，系统形成可执行计划，获取金融数据，以代码完成统计计算，组织有证据支持的研究报告，并在权限、预算或研究范围需要变化时请求确认。

首版核心场景：指定两至三家 A 股公司的对比研究。支持自定义目标，并提供一个完整示例：

2026-10-11 修正：比较研究作为验收示例，入口也支持知识问答、必要澄清、单股研究及多轮追问。下述功能方案不等于全部已上线，实际能力与新增验收见核心修复记录。

> 比较贵州茅台与五粮液最近 60 个交易日的市场表现和最近公开财务数据，列出经营差异、风险因素与尚待验证的问题，每个核心结论给出证据。

研究窗口根据交易日历解析，不将自然日等同于交易日。基准指数对比仅在指数历史数据实际可用时加入。财务分析明确报告期、披露时间和可比性；没有披露时间时不得假定历史时点已经知道相关数据。

用户可以追问、查看证据、暂停、继续、停止、重试失败任务及导出报告。后续研究形成新的 Run，并连接前一版产物和有效记忆。

首版以研究报告、历史表现图表、财务对比表和证据清单作为成果。输出不包含确定性涨跌预测、收益承诺或直接买卖建议。用户画像和持仓演示使用构造数据。

## 3. 产品界面

桌面主界面采用三栏工作台；窄屏改为研究、任务和成果标签页。

| 区域 | 用户可见内容与操作 |
| --- | --- |
| 左栏：研究空间 | 研究线程、标题、状态、最近更新时间；新建研究和打开历史研究 |
| 中栏：目标与运行 | 输入目标、查看和修改计划；任务状态、工具结果卡片、需要确认的操作；暂停、继续和停止 |
| 右栏：成果与依据 | 报告、历史图表、财务表、证据；点击结论打开原始字段或原文 |
| 运行详情抽屉 | 调用参数、数据时点、质量状态、耗时、token、成本估计、重试和检查点 |
| 设置页 | 服务配置状态、实际可用工具、默认预算、研究偏好及记忆查看/删除 |

首页提供一个示例目标和清晰的数据连接状态。默认展示最近已完成交易日的有效数据时点，盘中数据单独标注。产品正常流程使用“研究步骤”“来源”“继续研究”等词；内部技术字段保留在运行详情中。

动态界面由服务端事件驱动，不能用定时动画伪造工具执行。聊天中的文字、任务列表、报告和证据都来自同一次真实运行。

## 4. 技术架构与部署

采用模块化单体，降低部署与联调成本。

| 层 | 选择 | 职责 |
| --- | --- | --- |
| Web UI | Python 3.11 + NiceGUI；内置表格与 ECharts 组件 | 工作台、任务卡片、证据查看、报告与实时状态 |
| API | Python 3.11 + FastAPI + Pydantic | 输入校验、会话与资源权限、研究 API、事件流 |
| Agent 运行 | LangGraph + 持久化 SQLite checkpointer | 计划、工具选择、执行分支、审批、检查点及恢复 |
| 应用存储 | SQLite WAL + 本地持久化文件目录 | 线程、任务、调用账本、证据、记忆、审批、事件与产物 |
| 金融接入 | 扶摇 REST adapter；iFinD MCP adapter | 鉴权、工具发现、请求、错误解析与标准化 |
| 模型接入 | 可配置模型客户端 | 规划、证据内的综合、摘要与报告写作 |
| 部署 | Docker 单实例 + HTTPS + 持久化卷 | 对外可访问；重启保留研究状态和检查点 |

NiceGUI 在 Python 中定义页面、组件与交互，和 FastAPI 同源运行；浏览器资源由框架提供，项目不需要独立的 Node 构建流程。应用数据库与 checkpoint 数据库位于同一持久化卷。SQLite 版本只部署单实例，后台使用一个任务调度器；多个研究请求持久化排队，HTTP API、UI 长连接与执行任务分离。

NiceGUI 组件通过 Socket.IO/WebSocket 更新。界面订阅真实持久化事件，断线后按游标补回并查询状态快照；浏览器连接只负责展示与提交操作。FastAPI 的 SSE 接口保留为运行事件 API，两种传输共用同一事件记录。连接丢失后不依赖内存中的页面对象恢复研究。

后台调度器启动时扫描未完成 Run，通过租约与心跳识别中断任务；根据检查点进入恢复或待确认状态。浏览器关闭不会取消任务。任务实际取消由后端 stop/pause 请求控制。

模型和扶摇服务已在本机配置并补验通过；iFinD 与部署条件仍待配置验证。依赖已锁定于 requirements.lock；本机 WebSocket 已通过浏览器验证，跨平台镜像、公开 HTTPS、生产长连接与持久化卷仍需在实际部署环境验证。

## 5. 数据源与工具注册

### 5.1 接入策略

优先完成扶摇接口的真实请求，再扩展 iFinD MCP 的新闻、资金或宏观工具。题目允许以实际可调用能力为准，因此不把没有权限的接口列为已支持功能。

扶摇公开快速开始说明 REST 使用 `X-api-key` 鉴权，并返回含 `code`、`request_id`、`data` 的响应。财务指标文档说明业务错误可在 HTTP 200 下返回；adapter 必须同时检查 HTTP 状态、业务 code、结构与内容。

REST 工具使用显式 allowlist 和维护的契约注册；MCP 工具先通过 tools/list 发现，再根据权限和测试结果启用。启动时检查配置，在设置页区分“未配置”“待验证”“已验证”“无权限”“暂不可用”。模型只获得适用于当前研究的工具清单。

iFinD 登录页本轮未提供可解析的工具清单；实际 transport、鉴权、工具名称、字段和可用权限必须联调确认，方案不虚构端点。

### 5.2 首版逻辑工具

以下是 XBuddy 内部工具名，并非声称供应商已经提供同名接口。

| 内部工具 | 用途 | 启用条件 |
| --- | --- | --- |
| resolve_security | 将名称或代码解析为完整标的代码 | 实际检索能力可用；歧义时请求选择 |
| get_trading_calendar | 将研究窗口转换为交易日窗口 | 实际交易日历能力通过测试 |
| get_price_snapshot | 查询行情快照及其时点 | 实际快照接口通过测试 |
| get_daily_bars | 查询股票历史 K 线和复权口径 | 实际历史接口、权限及复权契约通过测试 |
| get_financial_metrics | 查询可比报告期的财务字段 | 实际财务接口通过测试 |
| get_index_bars | 查询基准指数历史 | 指数权限实际可用，否则计划显式省略 |
| search_financial_news | 获取可引用新闻原文和发布时点 | iFinD 或扶摇实际资讯工具可用，否则不生成新闻事实 |
| calculate_comparison | 计算历史表现及财务差异 | 本地确定性工具，输入必须引用已保存证据 |
| build_research_artifact | 生成版本化报告与导出文件 | 核心结论通过证据及表达校验 |

工具注册项包含：名称、描述、输入/输出 schema、供应商、权限组、是否收费/费用是否未知、超时、重试策略、版本、质量约束和证据提取方式。

调用记录保存规范化参数、开始/结束时间、供应商请求 ID、尝试次数、业务错误、结果指纹、费用状态和关联任务。密钥不进入提示词、浏览器、调用参数日志或证据。

### 5.3 数据状态

标准化结果同时保留原始记录与转换映射，使用 available / missing / stale / conflict / unauthorized / failed 等显式状态。合法空列表不等同于传输失败；null 不转成 0；未知单位不猜测；未知时点不默认现在。

记录 fetched_at、数据 as_of、报告期、披露时间和原始时间字段语义。响应生成时间不一定是行情时间或财报披露时间。历史分析固定截止时点；当前分析按交易日历和各数据类型更新频率判断新鲜度。

## 6. Agent Harness 主链路

运行路径：接收目标 → 解析研究范围 → 生成结构化计划 → 校验工具与预算 → 必要审批 → 执行任务 → 标准化数据与保存证据 → 确定性计算 → 综合研究 → 校验报告 → 保存产物。

当前入口先识别请求：一般解释进入回答；缺少必要信息进入持久化澄清；可执行研究进入规划。执行后由 review 节点观察可核验事实与目标覆盖，再决定有界补取、必要提问或综合回答。新增分支沿用原模型账本、预算、检查点和会话隔离。

执行过程中根据条件进入上下文压缩、有限重规划、暂停、等待确认或失败恢复分支。

### 6.1 计划与执行

Planner 生成经 Pydantic 校验的 Plan：目标、标的、截止时点、口径、任务、依赖、所需工具、预计调用数、数据前提和预计费用状态。

规划由模型根据目标和已启用工具完成，不能将每个问题都固定映射为同一组任务。执行器按依赖顺序调度；模型可以提出补充任务或改用可用工具，但代码校验权限、预算、参数和步骤上限。没有数据时不能凭模型知识补出“当前行情”。

首版计划最多 12 个任务，允许一次追加替代任务的重规划；未能覆盖的部分进入报告缺口。费用未知时明确标注，不将未知估计当作免费。

### 6.2 状态与停止规则

Run 状态：queued、running、awaiting_approval、paused、recovering、completed、partial、stopped、failed。每个 Task 独立记录状态和失败原因。

实际默认预算：最多 3 个标的、12 次工具尝试、4 次模型调用、100,000 模型 tokens、12,000 输入上下文 tokens（估算）、600 秒总时限。重试和失败调用计入预算；等待确认、暂停和停机仍计入总时限，可在预算设置中调整。

费用硬上限在调用前按已有账单和本次请求的保守预留校验。报价未知时使用可执行的调用次数上限，并展示费用未知；不能声称保证货币预算。超出允许范围之前请求确认，拒绝后继续较小范围或生成已有有效证据的部分结果。

暂停保存状态并允许继续；停止使本次 Run 终止且不再派发新调用。运行中的外部请求通过可取消等待和超时回收；无法撤销的已发请求仍记录其结果与费用状态。用户可以用已有材料创建新的研究 Run。

### 6.3 上下文压缩

上下文分为目标与约束、已验证研究记忆、任务摘要、最近消息和待处理问题。完整工具结果、历史材料和全部对话保存到存储，模型通过证据 ID 按需读取。

第五批采用输入上下文预算触发：预计输入超过该预算且压缩能减小体积时，将冗余事件历史替换为结构化摘要。目标、约束、完整计划、任务状态、审批、证据目录、口径和缺口原样保留。关键状态本身仍超预算时，在模型派发前请求扩大预算；拒绝后降级，不能静默删去约束。

摘要保存事件来源、原文范围、事件 ID 和指纹；原文与实际发送内容也保存完整指纹，读取时校验。结构化摘要不新增模型调用，也不成为新的原始证据。大响应通过证据存储保存，字段切片 API 支持按 ID 分页读取。

运行详情展示真实压缩事件、触发原因、前后 token 估计、模型和时间。正常流程可通过足量数据触发；测试模式降低阈值用于验证，不伪造压缩。

### 6.4 长期记忆

使用 SQLite 结构化记忆，首版无需向量数据库。保存明确表达的研究偏好、有来源的阶段研究事实和研究假设、未解决问题及下一次复核条件。

每条记忆包含作用域、类型、内容、证据引用、有效时点、有效期、版本和写入依据。用户明确保存的偏好可直接写入；从已验证研究口径推断的偏好以待确认建议展示。用户选中的事实自动绑定原报告、证据、单位、口径和历史时点，默认有效一天、最多 30 天；过期或依据不再可验证后停止引用。事实记忆仅作历史参考，本次核心结论必须由新运行的证据支撑。

支持查看、删除和修正。后续研究显示实际使用了哪些记忆。

### 6.5 检查点与恢复

使用持久化 LangGraph checkpointer。每次 Run 使用独立 graph thread_id，记录计划版本、运行配置和 schema 版本；用户研究线程下的不同 Run 不共用同一个执行游标。

每个工具/任务节点完成后保存检查点。副作用拆在审批之后的执行节点；恢复时使用调用账本和幂等键识别已完成工作，避免重复保存产物或重复执行已记录成功的调用。

幂等键含 Run、任务、工具版本和规范化参数。网络中断且供应商未确认的只读调用可能重试，记录重复尝试与可能费用，不能承诺外部服务“恰好一次”执行。

审批绑定 Run、计划版本、工具及参数指纹；参数或预算变化使旧审批失效。恢复先核对状态版本和需要的数据时效，再从未完成节点继续，不通过前端重新播放冒充恢复。

LangGraph 官方文档指出中断恢复会重新执行中断节点的前置代码，因此审批前仅进行纯计算和状态检查，将外部调用置于审批之后。

## 7. 权限与确认

| 操作 | 默认处理 |
| --- | --- |
| 已启用的只读金融查询、范围内的计算、报告生成 | 按用户研究目标自动执行 |
| 明显扩大研究标的、时间范围或增加预算 | 在新增工作前请求确认 |
| 标的歧义、不可兼容统计口径 | 请求用户选择，或明确省略相关比较 |
| 将模型推断的个人偏好写入长期记忆 | 请求确认 |
| 数据供应商权限不足 | 阻止调用并显示配置问题；用户点击确认不能代替供应商授权 |
| 确定性预测、收益承诺、直接买卖建议 | 转为事实研究与风险讨论，输出仍需表达校验 |

审批卡说明具体变更、理由、调用/费用增量及拒绝后的结果，支持批准、拒绝和修改。服务端原子消费决策，重复点击不会重复继续。批准不能解除数据真实性、证据和产品表达约束。

首版使用轻量会话认证。研究、证据、产物、记忆、审批和事件接口均校验所属会话，使用安全 Cookie，保护审批等写操作。公开演示使用隔离会话、构造用户资料和受限配额；可公开展示的市场字段还需符合数据授权。

## 8. 可验证研究成果

### 8.1 证据模型

结构化 Evidence 包含供应商、工具/接口、请求参数、请求 ID、原始记录/原文、字段路径或文本定位、as_of、fetched_at、报告期、单位、统计口径、质量状态和内容指纹。

DerivedMetric 包含公式、计算代码版本、输入证据 ID、输出数值和显示舍入规则。默认只计算已声明口径的历史区间表现、波动率、区间回撤及可比财务差异；复权不可得时明确标为未复权价格变化，不能称为总回报。财务累计指标与单季指标、不同报告期、币种和单位不能混算。

原始字段单位按实际供应商契约映射；不预设所有行情百分比均已除以 100。单位或定义不明确的指标进入待验证状态。

### 8.2 结论与报告

模型生成结构化 Claim：正文、fact / inference / uncertain 标签、证据或推导引用、时间边界、限制和待验证问题。事实需要原始证据；推断需要事实依据及限定语；无法验证的信息展示为未解决问题。

当前实现：模型读取已验证事实、目标和质量缺口，输出分项覆盖与带 F 编号引用的综合回答。代码检查目标所需字段、比较对象覆盖、数值占位符及来源指纹；失败最多修正一次，仍失败则保留原事实并说明原因。一般知识回答单独标明未进行本次金融核验。

报告包括研究问题与范围、摘要、市场表现、财务对比、风险与可能解释、数据缺口、待验证问题、证据与口径。图表的数据点可回到输入数据；核心结论点击后展开来源字段或原文。

保存报告 JSON、HTML/Markdown、CSV 财务对比表和证据索引；浏览器提供打印到 PDF。每个产物版本关联 Run、数据截止时点、输入证据指纹和校验状态。

证据校验检查引用、时间、数值和公式的一致性，并验证禁止输出的表达。规则匹配只是其中一层，结合结构化输出、数值复算、受控提示和人工检查。无证据的核心结论最多要求模型修正两次；仍失败时阻止发布该结论并说明原因。

合格部分材料可以发布为 partial，列明缺口；没有核心有效数据时标为 failed，提供错误说明和恢复操作。模型自评不等于事实验证。

## 9. 失败降级与可观测性

| 情况 | 处理 |
| --- | --- |
| 网络超时、限流和可重试错误 | 按错误类型最多额外重试两次，退避并计入预算 |
| 鉴权或 capability 权限错误 | 不盲目重试，标明缺少配置/权限 |
| 数据缺失、停牌或交易日不对齐 | 保留缺失状态；解释覆盖情况，避免填 0 或静默前向填充 |
| 缓存过期 | 默认获取新数据；使用历史缓存时显式标注其时点和用途 |
| 多来源冲突 | 同时展示数值、口径和时点；无法解决则不形成确定结论 |
| iFinD 新闻工具不可用 | 继续已有授权的量化研究，省略新闻事实及原因解释 |
| 模型失败或输出结构错误 | 有限重试；有配置才切备用模型；否则保留任务、证据和可恢复错误 |
| 报告模型不可用 | 以确定性表格与数据摘要输出明确标注的部分成果 |
| 服务重启/页面断线 | 持久化检查点恢复任务，事件游标补回 UI 状态 |

事件表使用单调递增 event_id。NiceGUI 界面记录事件游标，重连后从数据库补回并按状态快照重建组件；SSE API 支持 Last-Event-ID 补传。事件包括 plan.created、task.started、tool.finished、evidence.saved、context.compacted、approval.requested、checkpoint.saved、artifact.ready 和 run.failed 等。

运行详情呈现每阶段耗时、模型和工具尝试、token、成本估计/未知、缓存命中、质量问题与恢复记录。观测内容是可审计的操作轨迹和状态，不要求展示模型隐藏推理。

## 10. 工程组织与接口

```text
xbuddy/
  server/
    main.py                  # NiceGUI/FastAPI 同源入口
    ui/                      # Python 页面、组件、事件订阅与状态重建
    api/                     # 线程、运行、事件、审批、证据、产物
    harness/                 # graph、state、planner、executor、policy
    context/                 # 摘要和上下文装配
    memory/                  # 长期记忆与检索
    tools/                   # registry、扶摇/iFinD adapters、本地计算
    evidence/                # 来源提取、单位与口径、校验
    artifacts/               # 报告模型、渲染、版本与导出
    storage/                 # 数据表、迁移、调用账本、任务租约
  tests/                     # 单元、集成、E2E、边界样本
  docs/
    implementation-plan.md
    ai-usage.md
    verification-log.md
    testing.md
    known-limitations.md
  .env.example
  Dockerfile
  README.md
```

核心表：threads、runs、tasks、tool_calls、raw_records、evidence、derived_metrics、claims、artifacts、memories、approvals、run_events；checkpoint 由 LangGraph 持久化组件管理。

核心 API：

- POST /api/threads；GET /api/threads/{id}。
- POST /api/threads/{id}/runs；GET /api/runs/{id}。
- GET /api/runs/{id}/events。
- POST /api/runs/{id}/pause、resume、stop。
- POST /api/approvals/{id}/decision。
- GET /api/evidence/{id}；GET /api/artifacts/{id}；GET /api/artifacts/{id}/download。
- GET /api/tools；GET /api/memories；DELETE /api/memories/{id}。

API Key 由部署环境注入；生产日志脱敏。公开测试样本使用构造数据，受限原始数据仅在授权部署内保存，公开仓库不提交真实用户资料或受限响应。

## 11. 分批实施顺序

| 批次 | 工作 | 阶段出口 |
| --- | --- | --- |
| 1 | 验证模型、金融账号和部署条件；探测实际工具；锁定场景和依赖 | 至少一个目标金融源的真实调用成功；明确权限、字段和缺口 |
| 2 | 搭建 API、存储、工具注册、数据标准化和本地计算 | 可执行真实数据查询并保存可追溯输入与结果 |
| 3 | 实现计划、执行循环、审批、预算、停止和持久化检查点 | 后端可完整研究；可中断并恢复 |
| 4 | 实现 NiceGUI 三栏工作台、事件订阅、任务/证据/报告卡片 | 浏览器完成完整研究；断线后状态补回 |
| 5 | 实现压缩、长期记忆、报告校验、版本和导出 | 全部 Harness 必需机制能实际验证 |
| 6 | 主链路、数据异常、恢复和合规测试；修复问题 | 关键验收通过，失败有明确状态与恢复路径 |
| 7 | 部署、公开 URL 验证、仓库清理、README、AI/验证/测试记录 | 必交材料齐全；演示视频可选 |

如果第一阶段接口权限无法满足预定场景，应改选实际支持的数据与研究目标，并保留全部 Harness 要求。构造数据可用于开发和异常测试，但不能把构造市场数据标成真实，也不能用它证明真实工具已接入。指定源均不可访问时，记录阻塞并明确说明数据源边界，不能声称完成真实接入。

## 12. 验收与交付矩阵

| 原题要求 | 可操作验收 | 证据/材料 |
| --- | --- | --- |
| 能力/工具注册与计划执行 | 查看真实可用工具；自定义目标生成计划；工具实际返回数据 | 工具页、Plan、调用账本 |
| 上下文压缩 | 触发真实压缩；压缩后保持口径和证据引用 | 压缩事件、摘要、原文引用、回归检查 |
| 记忆 | 新研究使用有效偏好/阶段记忆；删除后不再使用 | 记忆页及实际使用记录 |
| 检查点与恢复 | 任务中途重启服务，继续未完成步骤 | checkpoint、前后调用记录与产物版本 |
| 权限与审批 | 扩预算时暂停；批准后继续；拒绝后遵守边界 | 审批卡、服务端校验与审计记录 |
| 停止规则 | 用户停止后不再派发调用；循环/预算达到上限时停止 | 状态与调用日志 |
| 成本/时延/可观测性 | 查看真实耗时、调用数、token 与费用状态 | 运行详情、事件和日志 |
| 线程/任务/证据/产物/动态 UI | 一个研究目标贯穿所有对象 | Web 主链路 E2E 与演示 |
| 数据失败及模型失败 | 故障注入后显示缺口、部分结果或可恢复失败 | 集成测试与 UI 验证 |
| 金融表达与可追溯性 | 每个核心事实可回到字段；无法验证的结论被阻止 | 报告校验与人工抽查 |
| 可访问、可操作 Web | 外部浏览器完成一次真实研究、审批与恢复 | 部署 URL、验证记录 |
| 源码与 README | 按说明可启动，锁文件与环境样例齐全 | 仓库 URL、README |
| AI 使用与验证记录 | 记录工具、参与环节、实际错误、人工修正及复验 | ai-usage.md、verification-log.md |
| 测试说明 | 覆盖主链路、缺失/接口失败、极端与合规场景 | testing.md 与实际结果 |

有意义的测试包括：HTTP 200 但业务 code 非零、合法空数据与 null、过期和冲突、未知单位、复权与交易日不一致、除零/负利润/极端价格变化、累计与单季财务混用、虚构证据引用、买卖建议请求、新闻文本中的提示注入、模型错误结构、预算耗尽、重复审批、暂停/停止、SSE 重连、压缩后引用完整、进程重启恢复和跨会话资源访问。

API/模型外部故障以构造响应完成可重复测试，同时另保留实际金融源的授权集成验证。测试记录写明环境、输入、预期、实际、通过/失败和已知限制，不把未执行的测试写为通过。

README 必须说明启动方式、环境变量、产品选择、AI 角色、数据来源、已知边界及未做事项。AI 记录随开发积累，记录真实发现与修正，不在提交前补写虚构过程。
